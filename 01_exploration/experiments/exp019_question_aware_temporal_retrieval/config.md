# exp019 config — Question-aware Retrieval + Temporal 확장

## 배경 / 이 실험이 왜 필요한가

지금까지의 진단 요약:

1. **"LLM이 답을 직접 생성"하는 모든 방식은 median/mode를 못 이김** — exp015 arm8/9(또래이탈 raw/narration), exp016(CANTRUST narrative)까지 일관됨. 유일하게 이긴 조건(exp015 arm10)은 leakage(twin 문항) 혼입 가능성이 있어 순수 기여로 보기 어려움.
2. **"LLM은 판단만, 실제 답이 최종 정답" 구조(exp017/018)로 바꾸자 처음으로 방향이 살아남** — 특히 exp018의 `arm_neighbor_target`(타겟 문항을 알려주고 이웃을 고르게 함)이 `arm_neighbor_raw`(일반 유사도)보다 두 타겟 모두에서 정확도·MAE 둘 다 나음(n=15×2라 유의성 미확정, p>0.15).
3. **응답자 전체를 typical(최빈값과 같은 답)/atypical(다른 답)로 나눠보면**, atypical 그룹은 지금까지 모든 방법이 눈에 띄게 못함(정확도가 typical의 절반 이하) — arm_mode는 원리적으로 atypical에서 0%. exp015 arm10만 atypical에서 균등무작위(20%) 대비 유의하게 나음(SATFIN 38.2% p=0.0004, PARTYLR 37.9% p=0.0012)이지만, "이미 atypical인 걸 아는 상태에서 2등 최빈값 찍기"라는 사후관측 상한(SATFIN 50%, PARTYLR 41%)에는 못 미침 — atypical 안에 아직 못 캔 구조가 남아있음을 시사.
4. exp018의 성공 요인을 일반화하면: **LLM이 "어떤 문항이 타겟 예측에 의미적으로 관련 있는지" 판단하는 건 유의미할 수 있는데, "30명 프로필을 한꺼번에 보고 느낌으로 순위 매기는" 유사도 계산 자체는 노이즈가 클 수 있다.** 이 두 역할을 분리하는 게 이번 설계의 핵심.

## 설계 원칙 (반드시 지킬 것)

- **최종 예측값은 항상 검색된 실제 이웃들의 실제 답변에서 나온다.** LLM이 타겟 문항의 답을 직접 생성하는 경로 없음.
- **LLM의 역할은 "어떤 문항이 관련 있는지 + 얼마나 중요한지" 판단으로 한정.** "누가 비슷한지"는 그 판단을 바탕으로 한 정량적 계산(거리/유사도)이 담당 — exp017/018처럼 LLM이 30명 프로필을 한 번에 보고 순위를 매기지 않음(그 자체가 노이즈원일 수 있어 이번엔 제거).

## 파이프라인

1. **(LLM, 타겟 문항당 1회만) 관련 문항 Top-K 선정 + 관련성 점수**: 타겟 문항 텍스트를 주고, `exp015_axis1_peer_deviation/lib_peer_deviation.py`의 `get_ordinal_candidates()`로 **순서형(ordinal)만 걸러진** 후보 풀(exp002의 153개 중 척도형만, exp015에서 이미 SATFIN/PARTYLR 각 98개로 확인됨 — z-score 거리 계산과 호환되도록 범주형/명목형은 애초에 후보에서 제외)에서, 이 문항에 대한 응답을 추론하는 데 **의미적으로** 관련 있는 문항 K개(K=8)를 고르고 각각에 1~10 관련성 점수를 매기게 함.
   - **배터리 쏠림 방지**: 프롬프트에 "같은 계열(예: 여러 기관에 대한 신뢰, 여러 조직 가입 여부)에서는 대표 1~2개만 고르고 서로 다른 주제의 문항을 다양하게 선택하라" 명시 (exp016에서 기관신뢰 배터리 6개가 21개 중 대부분을 차지했던 문제 재발 방지).
   - **다년치 커버리지를 2차 기준으로 반영**: 후보 목록에 `(7)kgss_variable_metadata.json`의 `n_years`(몇 개 연도에 조사됐는지)를 같이 보여주고, "**관련성이 최우선이고, 관련성이 비슷한 후보들 사이에서만** n_years가 높은(여러 연도에 걸쳐 조사된) 문항을 우선하라 — 이후 여러 연도 검색 풀 확장에 쓰일 것"이라고 지시. **주의**: 예전 axis1 arm3(이론적 개념군)이 "n_years desc → missing_rate asc"만으로 문항을 골랐다가 3개 타겟 전부 최하위를 기록한 전례가 있음 — n_years는 반드시 관련성 다음의 2차 기준으로만 쓰고, 1차 기준으로 격상시키지 않는다.
   - exp016처럼 "존재하지 않는 문항명 생성" 위험이 있어 **선정 결과를 VARDICT에 실존하는지 검증**하는 단계 필수.
2. **(계산, LLM 미사용) Question-specific Response Profile 구성**: 타겟 응답자 + 검색 풀 모든 응답자에 대해, 1단계에서 뽑힌 K개 문항의 **실제 응답값**을 추출(narration 없음, 있는 그대로).
3. **(계산, LLM 미사용) 유사도 계산 + Top-N 이웃 검색**: K개 문항 각각을 retrieval_pool 기준으로 표준화(z-score, lib_peer_deviation.py의 z-score 계산 재사용)한 뒤, 가중 거리로 유사도 계산.
   - **결측 처리**: 거리 계산은 타겟과 후보가 **공통으로 응답한 문항만**으로 계산(비어있는 항목은 건너뜀). 공통 응답 문항이 K개의 절반(4개) 미만인 후보는 이웃 후보에서 제외.
   - 가중치 3방식 비교:
     - **동일 가중치**: 모든 K개 문항을 똑같이 취급
     - **LLM 관련성 가중치**: 1단계 점수로 가중
     - **실제 \|r\| 가중치**: 1단계에서 LLM이 고른 **같은 K개 문항**에 대해, retrieval_pool로 실제 측정한 \|r\|(exp001/002와 동일 spearman 방식)을 가중치로 사용 — 문항을 통계로 고르는 게 아니라, 이미 LLM이 고른 문항의 가중치만 통계로 매기는 것이므로 axis1 원래 비판(통계로 문항 선별)과는 다름. "LLM의 관련성 판단"과 "실제 통계적 관련성" 중 뭐가 더 나은 가중치인지 직접 비교 가능.
4. **(계산, LLM 미사용) 최종 예측**: Top-N(N=8) 이웃의 실제 타겟 문항 답변을 median(척도형)/mode(범주형)으로 집계.
5. **(로깅)** 1단계에서 LLM이 매긴 관련성 점수와, 3단계에서 계산한 실제 \|r\|을 나란히 기록 — LLM이 "그럴듯하지만 실제론 무관한" 문항을 얼마나 골랐는지(CANTRUST 사례처럼) 사후 확인.

## 비교 arm

| arm | 유사도 계산 기준 |
|---|---|
| arm_mode | (없음, 검색 풀 전체 최빈값) |
| arm_demo_knn | 기존 9개 인구통계만 (exp014/017/018과 동일 기준선) |
| arm_qaware_equal | Question-aware K개, 동일 가중치 |
| arm_qaware_llmweight | Question-aware K개, LLM 관련성 점수 가중 |
| arm_qaware_statweight | Question-aware K개(LLM이 고름), 가중치만 실제 \|r\| |

**핵심 비교**: `arm_qaware_*` 3개가 `arm_demo_knn`(전체/일반 유사도)을 이기는가 — exp018의 "질문을 알려주면 낫다" 신호가 이 더 견고한(LLM 노이즈 제거한) 구조에서도 재현되는가. 그리고 `llmweight` vs `statweight` — 같은 K개 문항을 놓고 LLM의 관련성 판단이 실제 통계보다 나은 가중치인지, 못한지, 비슷한지.

## 시간범위 확장 (2단계, 기본 파이프라인 검증 후)

위 4단계를 검색 풀 범위만 바꿔 반복: **동일연도만(기존 방식) / ±1년(3개년) / ±2년(5개년) / 전체 17개년**. "몇 년치를 검색 풀로 쓸지"가 axis3 본연의 질문 — 1단계(관련 문항 선정)는 문항 자체의 의미 판단이라 연도와 무관하게 1회만 계산해 재사용.

## 스코프 (1단계 파일럿)

- 타겟: SATFIN, PARTYLR
- YEAR=2023 고정 (시간범위 확장은 이 결과 확인 후 2단계로)
- K(관련 문항 수)=8, N(최종 이웃 수)=8
- N_PILOT=15 (exp017/018과 동일하게 소규모 먼저)
- leakage 필터: 적용함(2026-08-08 정책) — 1단계 관련 문항 선정 후보 자체를 leakage 배제 통과한 것으로 제한

## 리스크

- 1단계에서 LLM이 존재하지 않는 문항명을 생성할 위험(exp016 HOUSSECUR 사례) — VARDICT 대조 검증 필수.
- K=8, N=8 모두 임의 설정값 — 파일럿 후 스윕 필요할 수 있음.
- K개 문항 중 공통 응답자 수가 너무 적으면(모듈 순환 때문) 이웃 후보 풀 자체가 줄어들 수 있음 — 파일럿에서 실제 커버리지 확인 필요.
